# 資安等級評定標準（草稿）

> **狀態：草稿，待主管與甲方範例確認後定案。** 目前版本是刻意保守的第一版，用來讓 `build_report.py`
> 產出的 Executive Summary 有一個明確、可重現、可跟甲方解釋的分級依據，而不是憑感覺下結論。

## 背景

甲方主要在意「這案子能不能放心交付」，看到報告裡列一長串「已忽略」的發現反而會緊張、逐條追問。
這份標準把 `classification.json`（Step 2 的 A/B/C 分類結果）壓縮成一個單一等級（A/B/C/D），
放在報告最前面的 Executive Summary，完整明細仍保留在後面章節與附件，供追問時查閱。

## 輸入資料

僅使用 `classification.json` 裡 `findings[]` 的兩個欄位：

- `impact`：Slither 回報的嚴重度（`High` / `Medium` / `Low` / `Informational` / `Optimization`）
- `category`：Step 2 人工分類結果（`A` 誤報 / `B` 可接受風險 / `C` 待人工確認），或缺漏（未分類）

## 判定邏輯（由上往下檢查，符合第一條就是該等級，不再往下看）

| 等級 | 條件 | 對甲方的說法（範例） |
|---|---|---|
| **D — 不通過** | 存在任一筆 `impact = High` 且 `category != A` | 「本案資安等級 D，偵測到 N 項高風險問題尚未排除，需修復並重新掃描後才可交付。」 |
| **C — 待確認，不建議此狀態交付** | 沒有上述 High 問題，但存在任一筆 `category = C`，**或任一筆完全沒有 `category`（未分類）** | 「本案資安等級 C，尚有 N 項待工程團隊人工確認事項，建議完成確認後再交付。」 |
| **B — 可交付，但需揭露已知風險** | 沒有 C 類、沒有未排除的 High，但存在任一筆 `category = B` | 「本案資安等級 B，無高風險項目，但有 N 項已知風險經工程團隊評估為可接受風險，詳見附件。」 |
| **A — 可直接交付** | 以上皆不符合 | 「本案資安等級 A，掃描範圍內無待處理或已知風險項目，詳見附件完整分類明細。」 |

沒有提供 `classification.json`（Step 2 還沒跑）時不計算等級，Executive Summary 改顯示「尚未評估」。

## 刻意保守的三個設計決定

1. **High 不能靠「B 類可接受風險」洗白。** High 只有兩條路：真的修掉（掃描結果不再出現），或被判定為誤報（A 類）。只要有 High 掛著 `category = B`，直接判 D，不留模糊空間。
2. **只要還有任何一筆 C 類，整體就不能是 A 或 B —— 不分嚴重度。** 哪怕只是一筆 Informational 的 C 類，也會把等級拉到 C。理由：C 類代表工程團隊自己都還沒把握，不該讓甲方誤以為已經處理完。
   - **已知取捨**：如果 C 類裡累積很多瑣碎的 Informational/Optimization 項目，會讓整體等級顯得比實際風險嚴重。之後如果覺得太嚴，可以改成「只有 High/Medium 的 C 類才影響等級，Low/Informational 的 C 類只在附件註記」。
3. **未分類的發現視同 C，而不是視同已解決。** 避免因為 Step 2 漏分類而讓等級虛高。

## 之後可能調整的方向

- 目前規則完全不看 `results_after.json`（Step 3 之後重新掃描的結果），只看 `classification.json` 本身的分類正確性。如果之後想交叉驗證「classification.json 說已排除的項目，是不是真的從 results_after.json 消失了」，可以再加一條額外的一致性檢查。
- 等主管提供的廠商範例、或跟甲方開會討論後，等級的命名（A/B/C/D vs 其他命名）與第 2 點的嚴重度篩選規則可能會再調整。
