# 情境式邏輯漏洞掃描（GPT-Scan 式）

> 方法論改編自 GPTScan（ICSE 2024，MetaTrust Labs：以 GPT 做程式理解、拆解邏輯漏洞為
> 「情境（scenario）＋特徵（property）」逐一比對，再以關鍵變數/語句確認降低誤報）。
> 本 kit 不外接 GPTScan 服務（需要 OpenAI API key 與其專屬靜態分析管線），而是把同一套
> 方法做成 Step 2 的**結構化檢查清單**，由執行流程的 AI 逐條比對、人工確認 —— 補的正是
> Slither 這類靜態工具抓不到的「業務邏輯層級」漏洞。
>
> 若之後要外接真正的 GPTScan 引擎（MetaScan 服務或其開源 prompts + 靜態管線），接點是
> `manual_findings[]`：外部工具輸出轉成候選、`scenario` 欄位標注來源、一樣走人工確認。

## 執行規則（不可跳過）

1. **領域事故模式調查（在規則 2 之前，同樣必須產出成實體文件）**：
   - **判定專案所屬業務領域**：RWA 代幣化、借貸協議、AMM/DEX、穩定幣、跨鏈橋、NFT、DAO 治理
     等，可能不只一種。
   - **先查共用庫，不要直接開始搜尋**：檢查 `references/domain_incidents/<領域>.md` 是否存在。
     - **存在** → 逐條套用該檔的「標準查證問題」查證回專案程式碼，逐條寫出「這在本專案存
       不存在」的結果。**此時不做網路搜尋**——公開資料的新鮮度是 repo 的維護責任（由
       `domain-library-refresh` 維護 skill 依 `last_reviewed` 負責），不該落在專案的關鍵路
       徑上。專案端重複搜尋既拖慢交付，又讓同領域不同專案的覆蓋深度取決於當次搜尋的手氣。
       套用前先讀該檔頭的 `last_reviewed` 日期，把它原樣記進本專案的 `audit/DOMAIN_RESEARCH.md`
       （例如「本次套用 `references/domain_incidents/rwa.md`，last_reviewed: 2026-05-01」）。
       若這個日期距今已明顯超過 3 個月門檻，**不要因此回頭重跑搜尋**（那是來源 A 的責任），
       但要在 `audit/DOMAIN_RESEARCH.md` 該段明確註明「此領域檔已逾刷新門檻，覆蓋深度可能過
       時」，並口頭告知使用者，讓過期狀態被看見，而不是悄悄照用。
     - **不存在** → 對該領域做一次真正的外部調查：使用網路搜尋工具查詢該領域公開的事故案例、
       審計公司部落格、資安公司的領域風險分析（如 CertiK／QuillAudits／Chainlink 這類文章）。
       **不能只依賴模型訓練資料的記憶**——訓練資料可能過時、不完整，也無法讓使用者追溯查證來
       源；每條歸納出的事故模式都要附可點擊的來源連結。第一個進入該領域的專案必付這個成本。
   - **整理成「領域事故模式清單」，比對回專案程式碼**：針對每條模式，明確寫出「這在本專案存
     不存在」的查證結果，而不是只列出模式本身。這份清單寫成專案自己的 `audit/DOMAIN_RESEARCH.md`。
   - **回饋共用庫**：若本次調查產生了庫裡沒有的領域層級模式（新建領域檔的情況是全部，既有領
     域檔的情況是讀碼時發現的新缺口），在 `audit/DOMAIN_RESEARCH.md` 末尾額外寫一個
     `## 待回饋至共用庫` 區塊，內容是**已去識別化、已套好條目模板、可直接複製貼上**的候選。
     **不要嘗試在 submodule 裡 commit**——完整的四階段回饋流程與去識別化規則見
     `references/domain_incidents/README.md`。
   - **為什麼這是強制的，不是選讀背景**：規則 2 的三份產出物完全從程式碼本身推導，不需要外部
     知識，因此只能發現「讀完全部程式碼才會注意到」的問題（成本較高、較慢）。領域事故模式調查
     提供的是「已知這個產業容易在哪裡出事」的**先驗知識**，讓後續讀碼可以優先往高風險的地方
     看，而不是均勻地讀完全部才發現問題；也可能找到規則 2／L1-L18 通用檢查完全不會觸及的缺口
     類型（例如某類系統的透明度／可稽核性機制缺失，這類問題往往不是程式碼「寫錯」，而是「沒
     有寫」，逐行讀碼看不出「沒有寫的東西」，只有先知道「這個領域通常應該要有什麼」才查得到）。
     這份清單與規則 2 的三份產出物、下表的通用情境庫，三者是互補關係，不能互相取代。
2. **前置產出物（在情境比對之前，且必須產出成實體文件，不能只在對話中口頭帶過）**：
   - **資產與托管地圖**：資產（代幣、資金、憑證）實際停在哪些地址／合約？誰能動它？
   - **特權角色權限表**：列出每個具名角色（owner／各種 operator／feeder 等）實際能呼叫
     哪些函式、後果多嚴重，依「觸發門檻 × 後果」分級。
   - **狀態機圖**（若合約存在多階段生命週期，即有 status／狀態欄位且被多個入口函式讀寫）：
     列出**每一個**能讀寫該欄位的函式與其轉換方向，逐一檢查轉換的現實世界語意是否對稱
     （例如「確認交貨」與「撤銷交貨」是否互為可逆的一組，還是其中一個轉換的效果會跟另一
     個轉換所代表的既成事實矛盾）。
   - **為什麼這是強制的，不是選讀背景**：下表 L1-L18 是**逐一情境、逐一合約**的檢查清單，
     本質上是局部檢查；但某些問題（例如 L12）只有在把同一合約裡多個函式的效果放在同一張
     狀態機圖上比較時才會浮現——單獨檢視任何一個函式都看不出矛盾。跳過此步驟直接跑
     L1-L18，會系統性漏掉這類問題。三份產出物請比照 `AUDIT_NOTES.md` 的形式寫成實體檔案，
     並在後續分類理由中引用，而非僅停留在推理過程。
3. **時機**：Step 2 分類時執行，對掃描範圍內的**每一份合約**跑完下表**全部情境**，
   不是「看到可疑才查」—— 系統性掃過一輪才是這個步驟存在的意義。
4. **兩段式判定（GPTScan 的核心，防止 LLM 憑感覺報漏洞）**：
   - **情境比對**：合約是否具備該情境的前置條件（例如「有轉出資產的函式」）？沒有 → 跳過。
   - **關鍵語句確認**：有 → 找出對應的關鍵變數/語句，**逐行讀實作**確認漏洞是否成立。
     不確定 → 仍然寫入 manual_findings，`category` 填 `D`（待確認），交給人判斷。
5. **證據要求**：每筆候選的 `dev_note` 必須引用關鍵語句位置（檔案:行號）與判定依據；
   「看起來怪怪的」不是發現。確認**安全**的情境不寫入 manual_findings，但若某情境的
   確認過程有值得留痕的邊界判斷，可在對話中回報給使用者。
6. **產出**：候選寫入 `classification.json` 的 `manual_findings[]`（格式見 SKILL.md），
   `scenario` 欄位填下表的情境編號（如 `"scenario": "L1"`），與其他人工發現一樣
   **必須經使用者確認**才算數。

## 情境庫

每條給出「情境比對」與「關鍵語句確認」兩段。這份清單是**下限保證，不是上限**——
不在本表情境內的邏輯問題仍依賴讀碼時的判斷力，看到就寫進 manual_findings。

| # | 情境 | 情境比對（何時需要查） | 關鍵語句確認（怎麼查） |
|---|---|---|---|
| L1 | 權限檢查實作錯誤 | 合約有任何 modifier 或 require 做呼叫者檢查 | 逐一讀實作：條件是否恆真/恆假（`\|\| true`、`==` 寫成 `=`）、比對對象是否可控（`tx.origin`）、owner 是否可被任意改寫 |
| L2 | 應保護而未保護的狀態變更 | 有會動到餘額、記帳、供給量、白名單等關鍵狀態的外部函式 | 該函式有沒有任何呼叫者限制？沒有的話，任何人呼叫會發生什麼？（增發、改帳、自毀） |
| L3 | 旗標/開關未落實 | 有 paused、locked、enabled 之類的狀態旗標 | 寫入旗標的函式存在，但讀取它的 require/modifier 是否真的出現在所有該擋的路徑上？只寫不讀＝裝飾品 |
| L4 | 缺滑點/最小輸出保護 | 有 swap、兌換、按匯率計算輸出的函式 | 使用者能否指定最小可接受輸出（minOut/deadline）？匯率來源在交易執行當下可否被操縱？ |
| L5 | 價格/匯率來源可操縱 | 讀取外部 oracle、AMM 儲備量、或單一來源價格 | 是否直接用 spot 值（`getReserves`、單點 `getRate()`）計價？無 TWAP/多來源/邊界檢查即可疑 |
| L6 | 首存者/份額計算操縱 | 有「按比例鑄造份額」的存款邏輯（shares = amount * totalShares / totalAssets） | totalAssets 為 0 或極小時，第一筆存款能否取得不成比例的份額？能否用直接轉帳灌大分母？ |
| L7 | 可搶跑的初始化/認領 | 有 initialize、claim、set-once 類函式 | 是否任何人都能先呼叫一次取得控制權/獎勵？部署與初始化之間是否存在競態窗口？ |
| L8 | 未授權轉帳 | 有代替他人轉移資產的函式（from 參數可指定） | `from != msg.sender` 時是否檢查 allowance？允許任意 from 即為任意轉帳後門 |
| L9 | 記帳順序錯誤 | 同一函式內既更新記帳（利息、獎勵、checkpoint）又移轉資產 | 記帳與移轉的先後順序反了會怎樣？（先付錢再扣帳 → 重入或重複領取；先更新匯率再結算 → 吃到錯誤匯率） |
| L10 | 重複計算/權重複用 | 有投票權、獎勵權重、快照類邏輯 | 同一份餘額能否透過轉帳在多個地址重複行使權重？快照時點是否可被操縱？ |
| L11 | 特權參數僅單側設界 | 特權角色（owner/operator）可設定的數值型參數（費率、折扣、容忍度等） | 是否只檢查了防止「更嚴格/更貴」那一側（如上限），卻沒檢查防止「趨近免費/趨近極端」的另一側？操作失誤（手滑、進位算錯）是否會讓任意使用者立即得利，且合約不會阻擋？ |
| L12 | 鏈上可逆狀態與現實不可逆事實矛盾 | 合約存在對應現實世界動作（交割、交貨、KYC 核准等）的狀態轉換，且該轉換之後仍存在「撤銷/退回」類函式 | 「撤銷」類函式操作的 status 檢查是否卡在轉換*之前*的狀態，還是也允許卡在代表現實已發生、不可逆之後的狀態？若後者，此函式的鏈上效果（如退還托管資產）是否會與現實中已完成、無法收回的動作（如已交付的實體資產）並存，造成同一份價值被兌現兩次？此情境需搭配規則 2 的狀態機圖執行，不能只看單一函式 |
| L13 | 「owner 信任地址」假設可被 owner 自行推翻 | Slither 或前一輪判斷因「外部呼叫對象為 owner 設定的可信合約，無 callback」而視為低風險的重入模式 | 該地址是否透過某個 `setXxx(address)` 函式可被 owner **事後**更換？若可，此低風險判斷的有效期只到下一次該 setter 被呼叫為止——換成任何帶 hook/callback 的合約類型（如 ERC777），原本的「無 callback」前提即失效，應重新評估為潛在重入風險而非直接排除 |
| L14 | 特權管制動作可被搶跑規避 | 合約存在「針對特定地址施加限制」的特權動作（加入黑名單、凍結、撤銷白名單、沒收等），且該動作需要一筆公開交易才生效 | 目標地址在該交易停留於 mempool 期間，能否搶先把資產轉走、或透過跨鏈橋移到另一條鏈上的新地址，使限制落空？限制生效**之前**的資產移動是否有任何延遲、暫停或原子性保護？注意這與 L3 不同：L3 是旗標根本沒被讀取，L14 是旗標讀取正確、但施加旗標的動作本身可被搶跑；兩者要分別檢查 |
| L15 | 跨鏈／多實例狀態在錯誤的一側被驗證 | 合約有跨鏈訊息收發（CCIP／LayerZero／自建 messager），且訊息路徑上存在對地址狀態的檢查（黑名單、白名單、KYC、餘額上限等） | 每個檢查是在**發送端**還是**接收端**執行？被檢查的狀態實際存放在哪一條鏈上？發送端檢查接收端才有的狀態＝無效檢查（恆為預設值），接收端缺少檢查＝限制可被跨鏈繞過。逐一比對「檢查位置」與「狀態所在位置」是否同一側，兩側都要看，只看單側會誤判為已保護 |
| L16 | 備援路徑的驗證強度低於主路徑 | 同一份資料有主要來源與備援來源（primary/fallback oracle、備援簽章者、替代結算幣等），且主路徑上有時效／邊界／權限檢查 | 逐一比對主路徑做過的每一項檢查，備援路徑是否**原樣做了一遍**？常見破法是備援分支只解構出「值」而丟棄驗證所需的欄位（如只取 answer 而捨棄 `updatedAt`，導致過期檢查形同不存在）。備援路徑通常在主路徑失效時才啟用——正是最需要驗證的時刻，卻往往是驗證最弱的一段 |
| L17 | 記帳依「意圖」而非「實際結果」，且失敗不回滾 | 存在「前置鉤子／中介層先記帳（額度、次數、配額、spent），實際動作稍後由另一個呼叫或另一個合約執行」的結構——ERC-4337 enforcer／caveat、middleware、guard hook 都是此形 | 記帳寫入的數值取自 calldata 的**意圖值**還是執行後的**實際轉出量**？執行路徑是否存在**不回滾的失敗模式**（`EXECTYPE_TRY`／try-catch／low-level call 不檢查回傳值／ERC20 回傳 false 而不 revert）？若兩者皆成立，攻擊者能否用必定失敗的執行反覆消耗額度造成 griefing，或反向讓實際轉出超過記帳？注意此情境**不是** L9：L9 要求記帳與資產移轉在同一函式內，本情境的記帳方根本不碰資產，L9 的前置條件不成立會被跳過 |
| L18 | 簽章雜湊未涵蓋全部應綁定的上下文 | 合約自行組裝待簽雜湊（`getXxxHash`、`_hashTypedData`、自訂 `abi.encode` 後 `keccak256`），而非完全沿用標準 EIP-712 domain separator | 逐一列出「同一份簽章在什麼條件下會被接受」：雜湊是否綁定了 chainId、verifyingContract（本合約地址）、nonce、以及**所有可替換的執行入口**（如 ERC-4337 的 EntryPoint、router、實作版本）？任何未納入雜湊的上下文，都代表同一份簽章可在該上下文的另一個實例上重放。特別檢查可升級或可多實例部署的系統：部署第二個實例、或官方更換 EntryPoint／router 之後，舊簽章是否仍然有效 |

## 情境庫的維護規則

任何一次掃描（不論哪個專案）事後被證實有本清單沒涵蓋的邏輯漏報時，回頭擴充情境庫：
新增或調整情境條目，並把「該案例 ↔ 命中情境」的對照記錄在案例自己的文件裡
（測試樣本記在 `test-fixtures/<名稱>/` 的 catalog，實際專案記在其掃描報告）——
本文件只放通用規則，不記錄個別合約的案例明細。修改既有情境時，用各 catalog 的
對照表回歸驗證同型問題仍會被抓到。

**案例對照（botgoldtoken，2026-08）**：L11 由折扣區間無下限（`GoldMarket._setDiscountTiersInternal`）
與 Oracle 報價無邊界（`GoldOracle._submitQuote`）兩個獨立案例共同歸納而來；L12 由 `revokeDelivered`
可在確認交貨後退還托管代幣（黃金雙重兌付）歸納而來，此案發現過程完全依賴規則 2 的狀態機圖，單獨
檢視 `revokeDelivered` 本身（含其存取控制）看不出問題；L13 由 `_refundAndBurn` 對外部 `applicant`
的轉帳（收款方經由可替換的 `_settlementToken` 間接可控）歸納而來。完整案例見該專案
`audit/AUDIT_REPORT.md` 的 M-01（L12）、M-02（L13）、M-03／M-05（L11）。

**案例對照（Matrixdock 回測，2026-08）**：L14 由「使用者可搶跑 `addToBlockedList` 交易，用一般轉帳或
跨鏈橋把資產移到新地址規避凍結」歸納而來；L15 由「發送端檢查接收端才有的黑名單狀態（恆為預設值，
形同無效檢查）」歸納而來。兩者皆來自公開的 Cyfrin Matrixdock 審計報告，經原始碼逐行驗證後寫入。
完整比對見 `docs/benchmarks/2026-08-12-matrixdock-rwa.md`。同一案例中「接收端 mint 完全未讀黑名單」
的子問題由既有 L3 命中，屬回歸驗證通過，未新增條目。L16 由同一次回測**自行發現**（不在 Cyfrin 報告
範圍內）的 `MTokenMain.increaseMintBudget` 歸納而來：主儲備 feed 取回 `updatedAt` 並做過期檢查，
備援 feed 的解構式卻捨棄該欄位，過期檢查在備援路徑上形同不存在。

**案例對照（MetaMask Delegation Framework 回測，2026-08）**：L17 由 `ERC20TransferAmountEnforcer`
與 `NativeTokenTransferAmountEnforcer` 在 `beforeHook` 以 calldata 意圖值累加 `spentMap`、而
`EXECTYPE_TRY` 模式下轉帳失敗不 revert（額度照樣被扣，可反覆 grief）歸納而來；L18 由
`getPackedUserOperationHash` 未把 EntryPoint 位址納入雜湊、導致同一份簽章可在另一個 EntryPoint 上
重放歸納而來。兩者對應 Cyfrin 報告的 M-1 與 H-1，經原始碼確認後寫入。**這兩條都是既有情境抓不到的**：
L9 要求記帳與資產移轉在同一函式內，enforcer 根本不碰資產，前置條件不成立即被跳過；簽章綁定上下文
則完全不在原有清單範圍內。完整比對見 `docs/benchmarks/2026-08-12-metamask-kms.md`。

**L17 的回歸驗證（同專案 part 2，2026-08）**：L17 寫成後，以撰寫時尚未讀過的 Cyfrin part 2 報告做非
循環驗證，命中其 M-1——同一個「前置鉤子以意圖值記帳、`EXECTYPE_TRY` 失敗不回滾」的缺陷出現在
另一組 enforcer（Streaming 系列，非 L17 來源的 TransferAmount 系列）。值得注意的是原專案在前一次
審計已修好 TransferAmount 系列，同型 bug 卻在 Streaming 系列留存兩週才被下一次審計發現——逐檔人工
審計會漏掉未排進當次範圍的同型實例，這正是規則 3 要求「對每一份合約跑完全部情境」而非「看到可疑才查」
的理由。

**規則 1 的案例對照（botgoldtoken，2026-08）**：對 RWA（實體資產代幣化）領域做外部事故調查後，
比對出 `GoldToken.sol` 沒有任何機制可讓外部驗證流通代幣量是否對應實體儲備（無 Proof of
Reserves）——此缺口不在既有 L1-L18 任何一條的偵測範圍內（它是「沒有寫的機制」，不是「寫錯的邏
輯」），純靠規則 2 的三份產出物或逐行讀碼也不會發現，需要先知道「這個領域通常應該要有儲備證明」
才查得到。完整調查見該專案 `audit/DOMAIN_RESEARCH.md`，發現收錄為該專案 `AUDIT_REPORT.md` 的
C-04。

## 領域事故庫的維護規則

規則 1 使用的 `references/domain_incidents/` 是一個**跨專案共用**的領域知識庫，與本文件上方
的 L1-L18 通用情境庫分工如下，兩者不可互相取代、也不可混寫：

| | L1-L18 通用情境庫（本文件） | 領域事故庫（`domain_incidents/`） |
|---|---|---|
| 收什麼 | 程式碼層級的通用漏洞模式，跨領域適用 | 特定業務領域「應該要有但沒寫」的機制缺口 |
| 怎麼發現 | 讀碼、比對情境、狀態機圖 | 領域先驗知識；逐行讀碼看不出「沒有寫的東西」 |
| 更新來源 | 專案事後證實的漏報（見上方「情境庫的維護規則」） | 公開事故研究為主，專案發現的領域層級缺口為輔 |
| 更新流程 | 直接修改本文件 | 依 `domain_incidents/README.md` 的四階段回饋流程 |

**分流判準**：一條新歸納出的問題，若換到別的業務領域仍然成立 → 進 L1-L18；若它的成立前提是
「這個領域的系統通常應該具備某機制」 → 進領域事故庫。判不出來時優先進 L1-L18，因為那條路徑
沒有跨專案的機密外洩風險。

**公開資料的新鮮度不由專案負責**：領域檔的 `last_reviewed` 欄位由 repo 維護者透過
`.claude/skills/domain-library-refresh/` 維護 skill 更新，門檻 3 個月，另支援人工強制觸發。
專案端執行規則 1 時，領域檔存在就直接套用，不要為了「怕過期」而重跑搜尋。
