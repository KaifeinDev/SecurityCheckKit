# 跨領域事故模式庫（domain_incidents）設計

**日期**：2026-08-12
**背景**：`references/logic_scan.md` 的 Rule 1（領域事故模式調查）目前每次執行都是臨時的、單次性的網路搜尋，只在 botgoldtoken 專案（RWA 領域）實測過一次，命中 Proof-of-Reserves 缺口案例（該專案 `AUDIT_REPORT.md` C-04）。這次調查的成果沒有被保留下來給下一個同領域專案重用。目標是把 Rule 1 從「每次臨時查」改造成「公司累積、跨專案共用」的領域情境庫。

## 動機

- 同一領域（RWA、借貸、AMM、穩定幣、跨鏈橋、NFT、DAO...）的專案容易踩中同一類已知事故模式，重複從零搜尋是浪費。
- Rule 1 存在的理由是「先驗知識能讓讀碼優先看高風險處」，但這份先驗知識目前不會累積。
- 對外交付審計報告的產品而言，**同領域專案的 Rule 1 覆蓋深度不該取決於那次搜尋的手氣**——一致性下限比效率更重要。

## 情境庫真正提供的價值（設計前提）

情境庫的價值**不主要在省下搜尋**，而在三件搜尋給不了的東西：

1. **checklist 推導的快取**：搜尋只給「這個領域出過什麼事」，把它轉成「我要在程式碼裡查什麼」才是貴且容易做歪的一步。
2. **去識別化的實戰案例**：「這條模式在我們自己的專案上真的命中過」是搜尋拿不到的自有資產。
3. **與 L1-L13 的對照關係**：這是 kit 專屬判斷，每次重搜都要重做。

再加上前述的**一致性下限**。效率是副產品，不是主要理由。

## 存放位置

新增 `references/domain_incidents/` 目錄，與 `logic_scan.md` 同層級，放在 SecurityCheckKit 本身（而非獨立 repo）。

**理由**：SecurityCheckKit 已是以 git submodule 形式被多專案共用的獨立 repo，跨專案累積知識與工具共用是同一個邊界。更關鍵的是**讀取每次審計都發生、寫入很少發生**，要優化常見路徑：放在 submodule 內讀取是免費的，寫入的 friction 另以下方「來源 B 回饋路徑」繞開。獨立 repo 的唯一優勢（權限切割）對內部工具不成立。

## 檔案結構

每個業務領域一個 Markdown 檔案：`references/domain_incidents/rwa.md`、`lending.md`、`amm.md`、`bridge.md`、`stablecoin.md`、`nft.md`、`dao.md`...。新領域出現時新建檔案，不預先窮舉。

檔案開頭包含：

- **`last_reviewed: YYYY-MM-DD`** — 上次完成公開資料刷新的日期，驅動下方的維護機制。
- **標題索引** — 各條目的 `D-<領域縮寫>-<編號>` 與一句話標題，讓 AI 快速掃過判斷要展開哪些條目，不必整份讀完。

## 事故模式條目模板

```markdown
## D-<領域縮寫>-<編號> <事故模式一句話標題>

- **描述**：事故模式的具體內容
- **來源**：<可點擊連結>（審計部落格／CertiK・QuillAudits・Chainlink 等資安公司文章／已知事件報導）
- **標準查證問題**：這在本專案存不存在？（1-3 條可直接照著查的具體問題）
- **對照 L1-L13**：命中 L5 / 或標「不在 L1-L13 涵蓋範圍（機制缺失類）」
- **實戰命中摘要**（去識別化，見下方規則）：
  2-4 句話描述「什麼類型的機制＋什麼問題＋什麼後果」，附命中日期（不含專案名）
- （若尚無命中案例，此欄留空，不寫佔位假案例）

---
```

## 隱私與去識別化規則

「實戰命中摘要」絕對不能讓跨專案讀者反推出來源專案：

- 不寫專案名稱、地址（合約／公司）、公司名稱。
- 不貼合約原始碼片段，也不貼函式名／變數名等可能間接識別的細節。
- 不寫具體金額或量級（TVL、發行量等），後果用抽象化說法（如「可能導致重複兌付」）。
- 只保留「什麼類型的機制＋什麼問題＋什麼後果＋命中日期」，讓任何人不需權限、不需點外部連結就能看懂這條案例學到什麼。

原始構想中「案例只留專案代稱＋連回專案自己的報告」的做法**不成立**：SecurityCheckKit 被不同存取權限的多個 repo 共用，其他人打不開那個連結。

## 執行流程（改寫 Rule 1）

1. 判定專案所屬業務領域（可能不只一種，沿用現行做法）。
2. 對每個領域檢查 `references/domain_incidents/<domain>.md`：
   - **存在**：逐條套用「標準查證問題」查證回專案程式碼，寫出查證結果。**不做網路搜尋**——公開資料的新鮮度是 repo 的維護責任，不該落在專案的關鍵路徑上（見下方維護機制）。
   - **不存在**：回退現行完整流程（地毯式外部調查）並建立該領域檔案。第一個進入該領域的專案必付這個成本，無法避免。
3. 整理成「領域事故模式清單」比對回專案程式碼（沿用現行 Rule 1 要求，不變）。
4. 若讀碼過程發現庫未涵蓋、且屬於領域層級的新模式，依「來源 B」路徑處理。

## 兩種更新來源（分開處理）

庫的更新有兩個性質完全不同的來源，機制必須分開：

### 來源 A：公開資料刷新（repo 維護責任）

公開事故資料與任何專案無關，不該由專案觸發。做成 **SecurityCheckKit 自己的維護 skill**：

- 位置：`.claude/skills/domain-library-refresh/SKILL.md`（在 SecurityCheckKit repo 內）。使用端專案把本 repo 掛載為 `.claude/skills/security-scan` 時，此路徑是巢狀的不會被載入——正確反映「這是給 kit 維護者、不是給接案工程師」的定位。
- 觸發：兩種方式並存——
  - **依新鮮度**：掃出 `last_reviewed` 超過 **3 個月**的領域檔案。
  - **人工強制**：維護者可指定任一領域檔案立即刷新，不論 `last_reviewed` 日期（例如該領域剛爆出重大事故、或即將接一個該領域的案子）。
- 執行者：初期由維護者手動觸發，之後可交由排程 agent 每季固定跑「依新鮮度」那條路徑。
- 工作內容：對選中的領域檔案做公開資料調查，補上新事故模式與新的標準查證問題，更新 `last_reviewed`，開 PR 等人審。
- **維護範圍天然有界**：領域檔案存在，代表曾有專案需要它。不會去養沒人接案的領域。

新鮮度門檻取 3 個月：領域層級的事故**模式**演進雖比個別事件慢，但區塊鏈資安整體演進快；且「人工強制觸發」已涵蓋突發狀況，門檻取短的代價只是維護頻率略高，比漏接新型模式便宜。

### 來源 B：專案發現回饋（去識別化，不卡關鍵路徑）

**審計過程完全不碰 submodule。** 工程師在專案裡跑審計時，`.claude/skills/security-scan` 是 detached HEAD 的 submodule checkout，在裡面 commit 既麻煩又容易掉；friction 高到會讓人乾脆不寫，庫於是永遠不更新。

改為以下四個階段。**階段 1 在審計關鍵路徑上，階段 2-4 不在**——沒有人會因為等 PR 而卡住審計進度。

#### 階段 1：審計當下（在專案 repo，AI 執行）

Rule 1 本來就在專案自己的 repo 產出 `DOMAIN_RESEARCH.md`。AI 在該檔末尾額外寫一個 `## 待回饋至共用庫` 區塊：

```markdown
## 待回饋至共用庫

> 狀態：未回饋 | 目標領域檔：references/domain_incidents/rwa.md

### 候選 1
<完整的、已去識別化、已套好條目模板的內容，編號欄留 D-RWA-?? 待回饋時指定>
```

內容必須**已去識別化、已套好模板、可直接複製貼上**——回饋者不需要重新編輯，只需貼上與指定編號。工程師的審計工作到此結束，這份檔案照常 commit 在自己專案裡。

#### 階段 2：回饋（在 SecurityCheckKit 的一般 clone，非 submodule）

預設由**跑該次審計的工程師本人**執行（有上下文才答得出 review 問題），也可累積數次後批次處理：

```bash
cd <你自己的 SecurityCheckKit clone>      # 不是專案裡的 submodule 路徑
git checkout main && git pull
git checkout -b domain-incidents/<domain>-<yyyymm>
```

1. 若 `references/domain_incidents/<domain>.md` **已存在**：把候選內容貼到檔案末尾，指定下一個未使用的 `D-<領域縮寫>-<NN>` 編號，並在檔頭索引補上這一行。
2. 若該領域檔案**不存在**（新領域）：以模板建檔，`last_reviewed` 填該專案做完整公開調查的日期——依 Rule 1，領域檔不存在時該專案確實做了一次地毯式搜尋，這個日期是有效的。
3. **不要因為新增案例而改動既有的 `last_reviewed`**：那個欄位只反映「公開資料刷新」（來源 A）的時點，與實戰案例累積無關。混用會讓來源 A 的維護排程誤判。
4. commit、push、開 PR。

#### 階段 3：PR review（去識別化把關）

**PR review 在此不是官僚流程，而是去識別化的第二雙眼睛**——檢查有沒有留下能反推出客戶的細節。這是唯一值得為 markdown 知識檔付 review 成本的理由。Reviewer 逐項確認：

- [ ] 無專案名稱、公司名稱、合約或公司地址
- [ ] 無合約原始碼片段，無函式名／變數名
- [ ] 無具體金額或量級數字
- [ ] 在完全不知道來源專案的前提下，這段摘要仍然讀得懂、學得到東西
- [ ] 條目編號未與現有條目衝突，檔頭索引已同步更新
- [ ] 「對照 L1-L13」欄位已填，且確認這條**確實屬於領域層級**（該有但沒寫的機制），而不是應該改走 L1-L13 維護規則的程式碼層級通用模式
- [ ] 未夾帶對**既有**領域檔 `last_reviewed` 的變更（新建領域檔則必須有此欄位，日期為該次完整公開調查日）

任一項不過 → 退回修改，不合併。

#### 階段 4：合併後回標（避免重複回饋）

PR 合併後，回到專案 repo 把 `DOMAIN_RESEARCH.md` 該區塊的狀態行改為：

```markdown
> 狀態：已回饋（D-RWA-03，PR #12） | 目標領域檔：references/domain_incidents/rwa.md
```

這一步是**冪等性所需**：沒有回標的話，同一專案下次重掃時 AI 會再產出一次同樣的候選，回饋者也無從判斷是否已處理過。

#### 並行衝突

風險低：不同領域是不同檔案，只有兩人同時改到同一領域檔才會衝突，且是純 markdown 的末尾追加，衝突解法就是各自佔一個編號。

### 與既有 L1-L13 維護規則的分工

`logic_scan.md` 末尾的「情境庫的維護規則」已在做「專案發現 → 歸納成通用情境 → 寫回 L1-L13」，L11/L12/L13 都是這樣從 botgoldtoken 長出來的。**程式碼層級的通用模式一律走那條既有路徑，不進領域庫。**

領域庫只收「這個領域**應該要有但沒寫**的機制」這類靠讀碼看不出來的缺口（C-04 Proof-of-Reserves 即是）。兩條路徑互補，不重疊。

## 範圍邊界（本次不做的事）

- 不改根目錄 `SKILL.md`（security-scan）——它只引用 `logic_scan.md`，改動發生在被引用文件內部，Step 2 既有描述仍成立。
- 不碰 `severity_grading.md`——與資安等級判定無關。
- 不建立獨立 repo。
- 不預先窮舉全部領域檔案——照實際接案領域逐一新建（YAGNI）。
- 排程 agent 自動化不在本次實作內，僅保留為維護 skill 的後續選項。

2. 改寫 `references/logic_scan.md` 的 Rule 1（含「領域檔存在就不搜尋」與階段 1 的 `## 待回饋至共用庫` 區塊產出要求），並新增「領域事故庫的維護規則」小節（放在既有「情境庫的維護規則」旁，說明兩者分工）。
3. `.claude/skills/domain-library-refresh/SKILL.md` 維護 skill（支援「依 3 個月新鮮度掃描」與「人工強制指定領域」兩種觸發）。
