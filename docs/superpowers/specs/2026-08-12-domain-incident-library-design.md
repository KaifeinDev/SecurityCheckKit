# 跨領域事故模式庫（domain_incidents）設計

**日期**：2026-08-12
**背景**：`references/logic_scan.md` 的 Rule 1（領域事故模式調查）目前每次執行都是臨時的、單次性的網路搜尋，只在 botgoldtoken 專案（RWA 領域）實測過一次，命中 Proof-of-Reserves 缺口案例（該專案 `AUDIT_REPORT.md` C-04）。這次調查的成果沒有被保留下來給下一個同領域專案重用。目標是把 Rule 1 從「每次臨時查」改造成「公司累積、跨專案共用」的領域情境庫。

## 動機

- 同一領域（RWA、借貸、AMM、穩定幣、跨鏈橋、NFT、DAO...）的專案，容易踩中同一類已知事故模式，重複從零開始搜尋是浪費。
- Rule 1 存在的理由是「先驗知識能讓讀碼優先看高風險處」——但這份先驗知識目前不會累積，每個專案都要重新建立。
- 需要在「累積效率」與「品質控管／跨專案隱私」之間取得平衡。

## 存放位置

新增 `references/domain_incidents/` 目錄，與 `logic_scan.md` 同層級的參考文件，放在 SecurityCheckKit 本身（而非獨立 repo）。

**理由**：SecurityCheckKit 已經是以 git submodule 形式被多個專案（如 bot-gold-token）共用的獨立 repo，跨專案累積知識與「工具本身被多專案共用」是同一個共用邊界；沿用同一套版控與 PR review 習慣（可比照 `logic_scan.md` 既有的「情境庫的維護規則」段落），不必為此新開一個 repo 增加同步負擔。獨立 repo 的唯一優勢（不同存取權限）目前不成立——這是公司內部工具，不需要對此做權限切割。

## 檔案結構

每個業務領域一個 Markdown 檔案：`references/domain_incidents/rwa.md`、`lending.md`、`amm.md`、`bridge.md`、`stablecoin.md`、`nft.md`、`dao.md`...。新領域出現時新建檔案，不強制預先窮舉領域清單。

檔案開頭放一份標題索引（各條目的 `D-<領域縮寫>-<編號>` 與一句話標題），方便 AI 快速掃過判斷要不要展開細節，不必整份讀完才能篩選相關條目。

## 事故模式條目模板

```markdown
## D-<領域縮寫>-<編號> <事故模式一句話標題>

- **描述**：事故模式的具體內容
- **來源**：<可點擊連結>（審計部落格／CertiK・QuillAudits・Chainlink 等資安公司文章／已知事件報導）
- **標準查證問題**：這在本專案存不存在？（1-3 條可直接照著查的具體問題）
- **對照 L1-L13**：命中 L5 / 或標「不在 L1-L13 涵蓋範圍（機制缺失類）」
- **實戰命中摘要**（去識別化，見下方「隱私與去識別化規則」）：
  2-4 句話描述「什麼類型的機制＋什麼問題＋什麼後果」，附命中日期（不含專案名）
- （若尚無命中案例，此欄留空，不寫佔位假案例）

---
```

四個欄位對應設計討論中確認的需求：事故模式描述＋外部來源連結（Rule 1 既有要求，不可省）、標準查證問題（checklist 化，讓下一個專案不用重新思考怎麼查）、已知命中案例（跨專案對照，看出哪條模式最常見）、與 L1-L13 情境編號的對照關係（釐清這條是「L1-L13 已涵蓋但值得補領域脈絡」還是「L1-L13 完全沒涵蓋的機制缺失類」）。

## 隱私與去識別化規則

「實戰命中摘要」欄位絕對不能讓跨專案讀者反推出來源專案，規則：

- 不寫專案名稱、不寫地址（合約地址／公司地址）、不寫公司名稱。
- 不直接貼合約原始碼片段，也不貼函式名／變數名等可能間接識別出專案細節的內容。
- 不寫具體金額或量級（TVL、代幣發行量等），用抽象化說法描述後果（例如「可能導致重複兌付」而非具體數字）。
- 只保留「什麼類型的機制＋什麼問題＋什麼後果＋命中日期」，讓任何人不需要權限、不需要點外部連結，就能看懂這條案例學到了什麼。

這是本次設計相對原始構想（案例只留「專案代稱＋連回專案自己報告」）的修正——原始做法在 SecurityCheckKit 被多專案（不同存取權限、不同 repo）共用的前提下不成立，其他專案的人無法打開該連結。

## 執行流程（改寫 Rule 1）

`references/logic_scan.md` 的 Rule 1 改為兩階段：

1. 判定專案所屬業務領域（可能不只一種，沿用現行做法）。
2. 對每個領域，檢查 `references/domain_incidents/<domain>.md` 是否存在：
   - **存在**：逐條套用「標準查證問題」查證回專案程式碼，寫出查證結果；同時做一次**輕量**網路搜尋，確認庫沒有明顯過時或遺漏近期事故（不必像庫不存在時那樣從零地毯式搜尋）。
   - **不存在**：回退現行完整流程（未涵蓋領域的地毯式外部調查）。
3. 整理成「領域事故模式清單」比對回專案程式碼（沿用現行規則2要求，不變）。
4. 若調查過程發現庫中沒有的新事故模式（庫本來就不存在整份新建，或庫存在但這次搜尋到新案例/新模式），依模板整理成候選草稿，**列給使用者看**，待使用者明確確認（含確認去識別化摘要的用詞是否足夠去識別化）後才寫入/合併進對應的 `domain_incidents/<domain>.md`。使用者若否決，該候選只留在該專案自己的 `DOMAIN_RESEARCH.md`，不進共用庫。

## 累積機制

- **觸發方式**：人工審核後合併，不做 AI 自動歸納寫入。理由：域事故庫是跨專案共用資產，誤判或品質不一的內容一旦進庫，會污染下一個專案的判斷，比現有 `manual_findings[]` 要求人工確認的理由更強（那裡出錯只影響單一專案的報告，這裡出錯會系統性影響所有後續使用同一領域庫的專案）。
- **合併時機**：Step 2 分類過程中，AI 產出候選後直接列給使用者看，跟現有「A/B/C/D 分類需使用者確認」走同一個確認關卡節奏，不另開新的審核流程。

## 範圍邊界（本次設計不做的事）

- 不改 `SKILL.md`——它只引用 `logic_scan.md`，改動發生在被引用文件內部，Step 2 的既有描述仍然成立。
- 不碰 `severity_grading.md`——與資安等級判定機制無關。
- 不建立獨立 repo。
- 不預先窮舉全部業務領域檔案——照專案實際遇到的領域逐一新建，YAGNI。
